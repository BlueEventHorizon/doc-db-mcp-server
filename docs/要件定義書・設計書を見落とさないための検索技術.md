# 要件定義書・設計書を見落とさないための検索技術

## はじめに

生成AIで開発を進めるとき、「必要な文書をどう見つけるか」は、[なぜ生成AIは「ドキュメントを読んで」と言っても読まないのか？](https://zenn.dev/k2moons/articles/ff6399ee33346e)の記事でも触れたように、かなり本質的な問題です。

検索と言っても `grep` の延長のように見えるかもしれません。しかし実際には、検索技術にはいくつか異なる系統があり、それぞれ得意・不得意がはっきりしています。

特に開発では、単に検索できることよりも、**必要な要件定義書や設計書を見落とさないこと**の方が重要になる場面があります。Web検索のように「上位数件がだいたい合っていればよい」とは限りません。

この記事では、開発文書検索を考える上で押さえておきたい4つの概念を整理します。

- lexical retrieval
- dense retrieval
- hybrid retrieval
- reranking

あわせて、`BM25`、`Embedding`、`vector search` といった周辺用語も、要件定義書・設計書の検索という文脈で位置づけます。

## 検索技術の全体像

要件定義書や設計書の検索を考えるとき、検索技術は次の4層で見ると整理しやすいです。

1. **lexical retrieval**
   文字列や単語の一致で探す
2. **dense retrieval**
   Embedding を使って意味の近さで探す
3. **hybrid retrieval**
   lexical と dense を組み合わせる
4. **reranking**
   いったん取った候補を、より高精度に並べ直す

これらは互いに排他的というより、役割の異なる部品です。

この記事で何度か出てくる `recall` と `precision` も、先に簡単に置いておきます。

- `recall`: 必要な文書をどれだけ漏らさず拾えるか
- `precision`: 拾った文書のうち、本当に関連する文書がどれだけ多いか

開発文書検索では、多少余計な文書が混ざることよりも、必要な要件定義書や設計書を取りこぼすことの方が高コストになりやすいです。この記事が主に気にしているのも、その意味での `recall` です。

:::message
この記事では、検索結果に多少ノイズが混ざることよりも、必要な文書を落とさないことを重視しています。開発では、その方が設計逸脱や手戻りのコストに直結しやすいからです。
:::

## lexical retrieval とは何か

`lexical retrieval` は、単語や文字列の一致に基づく検索です。日本語では「字句検索」と呼ぶのが近いと思います。

たとえば次のような検索は lexical retrieval の仕事です。

```text
REQ-002
doc_structure.yaml
SourceKit-LSP
migration
```

この方式の本質は、**書かれている語そのものを手がかりに探す**ことです。

### 代表例

- `grep`
- 全文検索
- SQLite FTS5
- BM25

### BM25 は何か

`BM25` は lexical retrieval の代表的なスコアリング手法です。
ElasticsearchやOpenSearchなどでも採用されています。

単純な全文一致より少し賢く、

- 珍しい語を高く評価する
- 何度も出てくる語を高く評価する
- 長すぎる文書を少し不利にする

といった調整が入ります。

つまり BM25 は「意味を理解している検索」ではなく、**字句検索をかなり強くしたもの**です。

### lexical retrieval の強み

- 固有名詞、識別子、文書IDに強い
- 完全一致してほしいケースで安定する
- 実装が軽く、速い
- なぜヒットしたかを説明しやすい

### lexical retrieval の弱み

- 言い換えに弱い
- 抽象的な要求に弱い
- 文書に書かれていない別表現は拾えない

たとえば、クエリが「キャッシュの永続化を改善したい」で、文書側が `ProjectMemory persistence` とだけ書いてある場合、字句検索だけでは取りこぼすことがあります。

## dense retrieval とは何か

`dense retrieval` は、Embedding を使ってテキストをベクトル化し、その近さで検索する方式です。

ここで重要なのは、検索が文字列一致ではなく、**意味的な近さの近似**に変わることです。

### Embedding と vector search

この2つは混同されがちですが、別物です。

- `Embedding`
  テキストをベクトルに変換する処理
- `vector search`
  そのベクトル同士の近さを使って検索する処理

Embedding は AI モデルの役割です。vector search は、その出力に対する数学的な近傍探索です。

### dense retrieval の強み

- 言い換えに強い
- 抽象的なタスク記述から関連文書を探しやすい
- クエリと文書の表現が少しずれていても拾える

たとえば、

```text
クエリ: 「ツール追加をしたい」
文書:   「MCP implementation guide」
```

のように語が完全一致していなくても、近い意味として拾える可能性があります。

### dense retrieval の弱み

- 文書IDや識別子に不安定なことがある
- 閾値設計を誤ると関連文書を落とす
- 長文を1ベクトルにすると論点が希釈される
- ヒット理由が説明しにくい

特に開発文書では、`REQ-002` や `SHA-256` のような識別子が重要です。dense retrieval はこうした完全一致ニーズに必ずしも強くありません。

## hybrid retrieval とは何か

`hybrid retrieval` は、lexical retrieval と dense retrieval を併用する方式です。

狙いは単純で、それぞれの弱点をもう一方で補うことです。

- lexical retrieval は固有名詞や識別子に強い
- dense retrieval は言い換えや抽象表現に強い

したがって開発文書検索では、かなり自然な発想です。

### hybrid retrieval の典型パターン

1. lexical で候補を取る
2. dense でも候補を取る
3. 両者を統合する
4. 必要なら最終判定する

統合方法にはいくつかあります。

- 単純な union
- RRF（Reciprocal Rank Fusion）
  - 順位を逆数にして足し合わせるシンプルな統合手法
- 重み付き和

小規模コーパスでは、まず単純な union でも実用になることがあります。

### hybrid retrieval の利点

- false negative を減らしやすい
- 固有名詞と意味検索の両方を扱える
- 運用上の安全装置として機能する

### hybrid retrieval の欠点

- 構成が少し複雑になる
- 候補数が増えやすい
- 最終判定をどうするかが重要になる

つまり、hybrid にすると自動的に正解になるわけではありません。**候補生成の安全性は上がるが、後段の整理が必要になる**という理解が正確です。

## reranking とは何か

`reranking` は、最初の検索で取れた候補を、より高精度なモデルで並べ直す処理です。

検索全体をいきなり高精度にやるのではなく、

1. まず軽く広く拾う
2. 候補だけ精密に見る

という二段構えにします。

### 何が嬉しいのか

- 候補生成では recall を優先できる
- 後段で precision を上げられる
- 全文書に重い判定をかけずに済む

### 何が難しいのか

- 遅くなる
- 実装が一段複雑になる
- 小規模コーパスでは過剰になることもある

文書数が数百件程度なら、reranking が本当に必要かはケース次第です。候補生成の時点で十分なら、無理に入れない方が単純で壊れにくいこともあります。

## 要件定義書・設計書の検索では何が難しいのか

一般的なWeb検索と比べて、要件定義書や設計書の検索には少し独特の難しさがあります。

### 1. 固有名詞と抽象要求が混在する

クエリには次の両方が出ます。

- `REQ-002`, `SourceKit-LSP`, `doc_structure.yaml`
- 「認証フローを見直したい」「キャッシュ永続化を改善したい」

前者には lexical retrieval が強く、後者には dense retrieval が強いです。

### 2. 見落としコストが高い

開発では、1件の要件定義書や設計書の見落としが、そのまま設計逸脱や再作業につながることがあります。

だから検索では、Web検索のような「上位数件が良ければよい」よりも、**必要文書を落とさないこと**が重くなりやすいです。

ここでは precision だけでなく、recall がかなり重要になります。

### 3. 長文仕様は希釈が起きやすい

設計書や要件書は長く、1文書の中に複数の論点を含みます。

すると dense retrieval では、

- 文書全体を1ベクトルにすると論点が薄まる
- 逆に chunk を細かく切りすぎると全体文脈を失う

というトレードオフが出ます。

この問題への対策としては、文書を章や見出し単位で構造化して検索しやすくする方法や、`Late Interaction` のように文書全体を1ベクトルに潰しきらない検索手法があります。ただし、どちらも実装や運用は一段複雑になります。このあたりは、要件定義書や設計書の検索をさらに改善していく上での次の論点だと思います。

## どの技術が「見落とし防止」に向くのか

万能な正解が1つあるわけではありませんが、要件定義書・設計書を見落としにくくするという観点では、だいたい次のように考えられます。

### lexical retrieval が向く場面

- 文書ID検索
- 固有名詞検索
- ルール文書の厳密な引き当て
- 実装を軽く保ちたいとき

### dense retrieval が向く場面

- タスク説明文からの関連文書探索
- 言い換えや抽象表現が多いとき
- 文書の命名が揃っていないとき

### hybrid retrieval が向く場面

- false negative を減らしたい
- 固有名詞も自然言語も同じ入口で扱いたい
- 開発支援のように見落としコストが高いとき

### reranking が向く場面

- 候補数が多い
- 上位順位の質をさらに上げたい
- 多少遅くなってもよい

## よくある誤解

### 「Embedding があれば字句検索はいらない」

そうとは限りません。

Embedding は意味の近さには強いですが、ID や識別子の完全一致は別の問題です。開発文書検索では、むしろそこが重要なことが多いです。

### 「BM25 は古いので弱い」

そう単純ではありません。

BM25 は semantic ではありませんが、固有名詞、専門用語、識別子が多い場面では今でも強いです。開発文書では十分に主役になれます。

### 「hybrid にすれば全部解決する」

それだけで解決するわけではありません。

hybrid は候補生成を安定させやすい一方で、候補統合や最終判定の設計が必要です。雑に混ぜると、単に候補が増えるだけになることもあります。

### 「reranking を入れれば高品質になる」

改善することはありますが、常に費用対効果があるわけではありません。コーパスが小さいなら、候補生成だけで十分な場合もあります。

## おわりに

要件定義書・設計書を見落とさないための検索技術を整理すると、

- lexical retrieval は「語そのもの」に強い
- dense retrieval は「意味の近さ」に強い
- hybrid retrieval はその両方を補完する
- reranking は候補をさらに精密に整える

という役割分担になります。

重要なのは、**自分の文書とクエリの性質に対して、何を最適化したいか**です。

特に開発では、単に速い検索よりも、必要な要件定義書や設計書を落とさない検索の方が価値を持つことがあります。

そのため、要件定義書・設計書の検索では「最速の単一手法」を探すより、どこで recall を確保し、どこで precision を整えるかを設計する方が重要かと思います。
