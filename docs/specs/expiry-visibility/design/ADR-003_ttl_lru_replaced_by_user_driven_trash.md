# ADR-003 TTL/LRU 自動削除を廃止しユーザー主導のゴミ箱方式へ転換する

## メタデータ

| 項目     | 値                        |
| -------- | ------------------------- |
| ADR ID   | ADR-003                   |
| Status   | accepted                  |
| 決定日   | 2026-07-08                |
| 関連設計 | DES-003, FNC-007〜FNC-013 |

## 1. コンテキスト

既存の TTL/LRU 自動削除ワーカー（`internal/expiry`）は、システム全体の chunk 数が上限を超えた場合、最終アクセスが最も古い KEY から自動的に物理削除する（EXP-02）。この判定は「他に削除候補があるか」を考慮せず、候補が唯一であっても削除を実行する。

実運用で、投入直後（まだ一度も `query` していない）の KEY が唯一の候補となり、他に削除できるものが無いまま無警告で物理削除される事故が発生した。原因は 2 点:

1. `UpsertRecord` の `ON CONFLICT` 節に `last_accessed_at` が含まれず、書き込み（upsert/sync）では更新されない。投入直後の KEY は常に「最終アクセスが最も古い」扱いになる
2. LRU 判定が候補件数を考慮せず、上限超過が解消するまで機械的に削除し続ける

## 2. 決定

doc-db（DB 層）は「削除すべきかどうかの判定」を一切持たない設計に転換する。DB の責務は、KEY ごとの正確な情報（chunk 数・doc 数・最終アクセス日時等）をユーザー・AI エージェントに届けることに限定し、削除の要否判断と実行はそれを見た人間・AI エージェントに委ねる。

削除実行そのものも即座の物理削除にはせず、「ゴミ箱」状態を経由させる。ゴミ箱投入はユーザーの明示的操作でのみ発生し、設定された猶予期間（デフォルト 3 日）を過ぎて初めて自動的に物理削除される。ユーザーは猶予期間中いつでも復活できる。**この方針を徹底するため、既存の即時物理削除ツール（`delete_index`）は廃止し、削除経路をゴミ箱投入（`trash_index`）に一本化する**（初版では `delete_index` を無改造で維持する案だったが、即時削除の抜け道が残ると本決定の目的自体が成立しなくなるため、レビューを経て修正した）。

## 3. 検討した代替案

| 代替案                                                                               | 棄却理由                                                                                                                      |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| LRU 判定に「候補が唯一なら削除しない」安全弁を追加する                               | 唯一かどうかに関わらず、DB が自動判定で削除すること自体がリスクの根本原因。安全弁を積み増しても別の誤判定シナリオが再発しうる |
| `last_accessed_at` の更新漏れのみ修正し、TTL/LRU 判定ロジックは維持                  | 判定ロジック自体（DB が「消してよい」と判断する設計）が事故の本質。個別バグ修正では同種の事故を再発防止できない               |
| TTL/LRU を廃止し、削除は全てユーザーの `delete_index` 呼び出しに一任（猶予期間なし） | 誤操作時の復元手段が無い。既存の `pending_deletions`（orphan の自己修復猶予）と一貫しない安全性になる                         |

## 4. 影響

**得られるもの**: DB が誤って重要データを削除する事故が構造的に発生しなくなる。削除は常にユーザーの意図した操作から始まり、猶予期間中は取り消し可能。

**失うもの**: 容量超過を DB が自動的に解消する機能が無くなる。運用者が KEY メタデータを定期的に確認し、能動的に整理する運用が必要になる。

**新たに生じる制約**: ゴミ箱投入から物理削除までの間、当該データは実データを保持したまま残るため、ディスク使用量は猶予期間分だけ余分に必要になる。

影響が及ぶコンポーネント種別: TTL/LRU 自動削除ワーカー、KEY メタデータ提供 MCP ツール、KEY 単位の廃棄ポリシーオーバーライド機能。詳細な変更対象は DES-003 を参照。
