# ADR-001 追加feature判定は「新規要件定義書の作成有無」だけでなく実質的な影響範囲で行う

## ステータス

承認

## コンテキスト

`desired-state 同期ジョブ + 削除予約の起動時ガベージコレクション`（APP-001 FNC-006 / DES-003）を設計する際、以下の手順を踏んだ:

- 新規の要件定義書ファイルは作らず、既存の `APP-001_doc_db_mcp_server_requirements.md` に FNC-006 節を直接追記した
- `additive_development_spec.md` §1 の適用条件（「要件定義書を新規作成する」）を機械的に適用し、「新規要件定義書を作っていない」ことを根拠に追加feature扱いではないと判定した
- そのため `DES-003` にも `type: temporary-feature-design` frontmatter を付与せず、`docs/specs/base/design/` に直接作成した

一方でこの変更は実質的に:

- 新規 MCP ツールを 3 つ追加する（`sync_documents` / `get_sync_status` / `schedule_delete_series`）
- 新規永続テーブル（`pending_deletions`）を追加する
- サーバー起動シーケンスを変更する（起動時スイープ）
- 既存の廃棄方針（DES-001 §8.3「series の自動廃棄は実装しない」）と正面から矛盾する

`/forge:merge-specs` を別件（`base`/`install` の統合要否）で検討した際、このskillの存在自体が「featureは分離ディレクトリで作業し、完了後にmergeで正本へ統合する」運用を前提にしていることに気づいた。今回のように成果物を最初から `base` に直接書いてしまうと、後から `merge-specs` で整理する手段を使えず、`base` の中で新旧の記述が矛盾したまま残る（実際に DES-001 §8.3 が §8 冒頭の注記と矛盾した状態で放置されていた）。

## 決定

`additive_development_spec.md` §1 の「要件定義書を新規作成するか」という条件は、**AI が既存文書への直接追記を選ぶことで容易に回避できてしまう** ため、単独の判定根拠として不十分と判断する。今後、以下のいずれかに該当する変更は、要件定義書を新規作成したかどうかに関わらず追加feature（`temporary-feature-*` frontmatter + 専用ディレクトリ）として扱う:

- 新規 MCP ツール / 新規 API エンドポイントを追加する
- 新規の永続データ構造（テーブル・スキーマ）を追加する
- 既存の起動シーケンス・既存の恒常プロセス（ワーカー等）の挙動を変更する
- 既存の設計書に明記された既存方針と矛盾・置き換えが発生する

これらのいずれにも該当しない小規模な追記（誤字修正・表への行追加・既存節の言い回し変更等）は、従来通り既存文書への直接編集で構わない。

判定に迷う場合は、上記チェックリストを提示したうえで `additive_development_spec.md` §0 の判定に立ち返り、AskUserQuestion で確認する。

## 影響

- `additive_development_spec.md` §1 の運用時解釈として、本 ADR のチェックリストを併用する
- 既に `base` に直接作成済みの FNC-006 / DES-003 の扱い（retrofit するか現状のまま進めるか）は本 ADR のスコープ外とし、別途ユーザー判断に委ねる
